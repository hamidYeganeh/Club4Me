# اجرای مسیر کامل رزرو روی دستگاه واقعی

این runbook مسیر `کشف → جزئیات → سانس → رزرو → پرداخت → اعلان → لغو/refund`
را برای یک build امضاشده و backend production-like تعریف می‌کند. E2E مرورگر جای
این دور را نمی‌گیرد.

## پیش‌نیاز

- گوشی واقعی با `adb devices` در وضعیت `device`، نه `unauthorized`.
- AAB نصب‌شده از Internal testing یا APK release امضاشده.
- `NEXT_PUBLIC_API_URL` عمومی و HTTPS، نشان و Firebase واقعی، و یک حساب تست با
  شماره‌ای که SMS دریافت می‌کند.
- باشگاه/سانس تست با ظرفیت، قیمت و policy بازپرداخت معلوم.
- دسترسی فقط‌خواندنی به logهای API، Sentry، Firebase delivery و رکوردهای
  payment/ledger برای تطبیق نتیجه.
- درگاه پرداخت sandbox یا production با تراکنش کم‌مبلغ. provider فعلی پروژه
  `mock` است؛ بنابراین تأیید «پرداخت واقعی و refund بانکی» تا اتصال درگاه واقعی
  ممکن نیست.

## اجرای اصلی

| گام | اقدام روی گوشی                         | شاهد مورد نیاز                                                  |
| --- | -------------------------------------- | --------------------------------------------------------------- |
| ۱   | نصب تمیز، ورود با OTP و اجازه اعلان    | زمان SMS، user id تست و نسخه اپ                                 |
| ۲   | جست‌وجوی باشگاه و بازکردن نتیجه        | screenshot نتیجه و request id                                   |
| ۳   | بررسی جزئیات، قوانین لغو و انتخاب سانس | session id، ظرفیت قبل از رزرو                                   |
| ۴   | تأیید رزرو با double tap کنترل‌شده     | فقط یک reservation id و یک کاهش ظرفیت                           |
| ۵   | پرداخت و بازگشت به اپ                  | payment intent/authority و وضعیت paid                           |
| ۶   | بررسی اعلان                            | اعلان درون‌اپ، Push در foreground/background و SMS              |
| ۷   | لغو رزرو                               | متن policy، درصد و مبلغ refund پیش از تأیید                     |
| ۸   | تأیید refund                           | reservation cancelled/refunded، ledger متوازن و reference درگاه |

پس از گام ۸، همان لینک اعلان را باز کنید: اپ نباید عملیات منقضی یا غیرمجاز را
دوباره اجرا کند و باید وضعیت نهایی لغوشده را نشان دهد.

## دورهای خطا

1. Airplane mode: باید «آفلاین» دیده شود و پس از اتصال retry موفق باشد.
2. latency بیشتر از timeout: باید «پاسخ‌گویی طول کشید» دیده شود، بدون رزرو
   تکراری.
3. پاسخ 500: باید server error مستقل نمایش داده شود و request id قابل پیگیری
   باشد.
4. رد location/notification: باید permission denied و مسیر Settings نمایش داده
   شود، نه خطای شبکه.
5. جست‌وجوی معتبر بدون نتیجه: فقط empty state نمایش داده شود.

## ثبت نتیجه

برای هر دور، version code، Android/WebView، نوع شبکه، timestamp، شناسه‌های
reservation/payment/refund، اسکرین‌شات‌ها و لینک Sentry/log را کنار گزارش
Internal Release نگهداری کنید. اطلاعات کارت، OTP، access token و شماره کامل
موبایل نباید در شواهد قرار گیرد.

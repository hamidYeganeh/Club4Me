# راه‌اندازی آمار و PostHog

پروژه `Club4Me` در EU Cloud با شناسه `273193` راه‌اندازی شده و کلید دریافت در فایل محلی و خارج از Git بک‌اند تنظیم شده است. در ۲۰۲۶-۰۹-۱۳ ارسال آزمایشی پاسخ HTTP 200 گرفت و رویدادهای `app.opened` و identify در Activity دیده شدند؛ رویداد آزمایشی با `environment=development` و `setup_test=true` مشخص شده است. این تأیید دریافت خارجی است، نه تأیید استقرار نسخه جدید روی سرور production.

داشبوردهای نهایی و غیرعمومی: [محصول](https://eu.posthog.com/project/273193/dashboard/949658) (۷ گزارش) و [باشگاه‌ها، فقط تیم داخلی](https://eu.posthog.com/project/273193/dashboard/949664) (۳ گزارش). یک داشبورد اضافی با نام `Draft · Club4Me Product (superseded)` نگه داشته شده و مرجع گزارش نیست.

تنظیمات انتشار در `.env.posthog.production` خارج از Git آماده شده و `deploy/prepare-production-env.mjs` آن را به فایل محیطی production منتقل می‌کند. این فایل فقط سه متغیر ارسال PostHog دارد و حاوی کلید مدیریت نیست. اجرای deployment و restart سرور در این مرحله انجام نشده است.

## چه چیزی آماده شده؟

- ادمین `/analytics`: فعال روزانه/هفتگی/ماهانه، ثبت‌نام، رزرو، درآمد دفتر کل، مقایسه دوره قبل، قیف مرتب، بازگشت هفتگی، سلامت درخواست‌ها، باشگاه‌های پرتراکنش و ساعات پرطرفدار.
- بیزینس، داشبورد اصلی: گزارش فقط برای باشگاه انتخاب‌شده، مشتری جدید/برگشتی، ظرفیت، تمدید و عضویت‌های نزدیک انقضا، نظرات بی‌پاسخ، دریافت آنلاین و سهم مجموعه. دریافت حضوری و گزارش حضور در بخش‌های قبلی داشبورد حفظ شده‌اند.
- تاریخ شمسی، بازه‌های ۷/۳۰/۹۰ روز، پایان دلخواه در ۹۰ روز گذشته، مقایسه هم‌اندازه، CSV و وضعیت خالی/خطا.
- `PosthogDeliveryService`: صف پایدار در همان رکورد رویداد، ارسال دسته‌ای، timeout، backoff، UUID ثابت و توقف تمیز هنگام shutdown.
- `OutcomeSyncService`: استخراج نتایج از رکوردهای **commit‌شده** پرداخت و رزرو، بدون وابسته کردن تراکنش تجاری به PostHog. شروع تاریخچه نتیجه‌ها از اولین اجرای این نسخه است؛ داده قدیمی خودکار به سرویس خارجی backfill نمی‌شود.

## تنظیم اتصال

۱. پروژه فعلی روی پلن رایگان و منطقه EU است. همه insightهای راه‌انداز به‌صورت پیش‌فرض `environment=production` را فیلتر می‌کنند؛ محیط محلی `development` است. در صورت فراهم بودن پروژه دوم، جداسازی پروژه‌های production و development هم ممکن است.

۲. در `apps/backend/.env` یا secret manager محیط اجرا:

```dotenv
POSTHOG_PROJECT_TOKEN=phc_your_project_token
POSTHOG_HOST=https://eu.i.posthog.com
POSTHOG_ENVIRONMENT=production
```

`POSTHOG_ENVIRONMENT` باید دقیقاً با `NODE_ENV` برابر باشد. برای US، میزبان دریافت `https://us.i.posthog.com` است. برای سرور اختصاصی از نشانی HTTPS آن استفاده کنید. این متغیرها server-only هستند؛ کلید شخصی را در `NEXT_PUBLIC_*` نگذارید. فایل env واقعی را commit نکنید.

۳. بک‌اند را با محیط جدید restart کنید. پس از ثبت رضایت تحلیل، اپ را باز کنید، یک باشگاه ببینید و رزرو آزمایشی انجام دهید. در PostHog رویدادهای `app.opened`، `discovery.club_viewed` و سپس نتایج سرور را بررسی کنید. ثبت نتایج سرور معمولاً حدود یک دقیقه تأخیر دارد. قسمت «تعریف آمار» در ادمین تعداد pending و retry را نشان می‌دهد؛ configured فقط وجود تنظیمات است و تأیید اتصال نیست.

۴. retention داده در پروژه PostHog را متناسب با سیاست حریم خصوصی خود تنظیم کنید. TTL داخلی ۱۸۰ روز است؛ پاک‌شدن داخلی به معنی پاک‌شدن خودکار در PostHog نیست. ضبط نشست و autocapture فعال نشده‌اند؛ هیچ تصویر صفحه، ورودی فرم، متن جست‌وجو، شماره تماس یا موقعیت دقیق ارسال نمی‌شود. برای درخواست حذف داده خارجی از ابزار حذف شخص/رویداد PostHog با distinct ID `user:<id>` استفاده کنید؛ پس از حذف حساب/لغو رضایت، ارسال رویدادهای جدید و pending آن کاربر متوقف می‌شود.

## ساخت داشبوردهای خود PostHog

پیش‌نمایش تعریف داشبوردها بدون شبکه و کلید:

```sh
node scripts/setup-posthog.mjs --dry-run
```

برای ساخت واقعی، این متغیرها را در محیط محلی محافظت‌شده قرار دهید:

```dotenv
POSTHOG_API_HOST=https://eu.posthog.com
POSTHOG_PROJECT_ID=12345
POSTHOG_PERSONAL_API_KEY=your_personal_key
```

کلید شخصی برای راه‌انداز به scopeهای خواندن و نوشتن dashboard و insight نیاز دارد. سپس از ریشه پروژه:

```sh
node --env-file=apps/backend/.env scripts/setup-posthog.mjs
```

این فرمان دو داشبورد داخلی و ده insight می‌سازد. همه آن‌ها به‌صورت پیش‌فرض فقط رویدادهای production را می‌خوانند؛ `POSTHOG_REPORT_ENVIRONMENT=development` برای راه‌اندازی در یک پروژه توسعه جدا قابل استفاده است. اجرای دوباره، موارد هم‌نام موجود را به‌روزرسانی می‌کند. داشبورد دوم برای تیم داخلی است؛ آن را عمومی نکنید و به بیزینس‌ها share نکنید. بیزینس‌ها فقط endpoint محافظت‌شده خود برنامه را می‌خوانند.

## قرارداد و تعاریف

- منبع مالی: `payment_intents` و `ledger_entries`؛ همه مبالغ ریال. خریدهای پرداخت‌شده شامل درگاه و کیف پول هستند. بازپرداختِ نمایش‌داده‌شده متعلق به خریدهای همان دوره، با وضعیت تا زمان تهیه گزارش است. سهم درآمد از تاریخ ثبت دفتر کل محاسبه می‌شود.
- پرداخت آنلاین فعلی پروژه mock/غیرفعال است. روی داشبورد مشخص شده و در PostHog نتیجه‌ها `payment_mode=simulation` دارند.
- منبع رفتار: رویدادهای دارای رضایت نسخه `2026-09-13`. تعداد فعال، نماینده کاربران دارای رضایت است؛ درخواست‌های خودکار API به تنهایی کاربر را فعال حساب نمی‌کنند.
- قیف داخلی مخصوص رزرو سانس است؛ خرید بسته، عضویت و ثبت‌نام مربی پرداخت‌های جدا دارند. مراحل باید به ترتیب در بازه رخ داده باشند. قیف هویت‌ها را می‌سنجد، نه تک‌تک سفارش‌ها.
- cohort اولین رزرو **مشاهده‌شده در تاریخچه موجود** است؛ سابقه کامل عمر کاربر نیست. هفته‌های ناقص `null` هستند. هفته از شنبه و روز با منطقه تهران تعیین می‌شود.
- ظرفیت و نزدیک‌انقضا همیشه snapshot فعلی/هفت روز آینده‌اند، حتی اگر بازه گذشته انتخاب شود.
- رفتار بیزینس با `properties.club_id` محدود می‌شود؛ رزرو و مالی با clubId/ownerId سمت سرور. پارامتر query نمی‌تواند این محدودیت را تغییر دهد. `reports.read` الزامی و آمار مالی نیازمند `payments.read` است.
- صف مرورگر حداکثر ۱۰۰ رویداد است. ارسال همزمان رویداد جدید باعث حذف آن از صف نمی‌شود؛ خروج/تغییر حساب، صف و شناسه نصب مرتبط را جدا می‌کند.
- نتایج تجاری توسط worker از رکوردهای commit‌شده استخراج می‌شوند. cursor پایدار و بازخوانی ۵ دقیقه اخیر، replay را پوشش می‌دهد. در محیط با تراکنش‌هایی طولانی‌تر از این پنجره، پنجره را افزایش دهید یا change-stream/outbox تراکنشی به کار بگیرید.
- گزارش رفتار فعلی تاریخچه حداکثر ۱۸۰ روز را از MongoDB می‌خواند. با افزایش حجم، aggregate روزانه یا query سمت PostHog جایگزین این خواندن شود؛ گزارش مالی باید از منبع حسابداری باقی بماند.

## رویدادها و نگهداری

مرجع نام‌ها `packages/api/src/tracking/events.ts` و نسخه متناظر بک‌اند است؛ قراردادها در `.telemetry/tracking-plan.yaml` و DTO سخت‌گیرانه ثبت شده‌اند. تغییر رویداد باید هر دو registry، types، wrapper، DTO و طرح را همزمان تغییر دهد. نتایج رزرو/پرداخت قدیمی از سمت کلاینت پذیرفته ولی عمداً ذخیره نمی‌شوند؛ برای جلوگیری از گزارش جعلی فقط منبع server شمرده می‌شود.

## بررسی‌ها

```sh
cd apps/backend
node ../../node_modules/jest/bin/jest.js --runInBand --runTestsByPath test/telemetry.e2e-spec.ts src/modules/telemetry/analytics-math.spec.ts src/modules/telemetry/posthog-delivery.service.spec.ts src/config/env.spec.ts
```

تست‌های خودکار اتصال از MongoDB موقت و PostHog mock استفاده می‌کنند. یک batch واقعی شامل identify، group و track نیز ارسال شد؛ Activity دریافت identify و `app.opened` و اتصال گروه روی رویداد را تأیید کرد. هیچ رویداد production ساختگی ارسال نشده است.

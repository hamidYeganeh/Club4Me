# فیچرلیست MVP Gym4Me

> نسخه: 0.4
>
> تمرکز: کشف و رزرو باشگاه، مربی و کلاس + مدیریت سانس
>
> وضعیت: MVP

## 1. تعریف محصول

Gym4Me در نسخه اول یک پلتفرم کشف باشگاه، مربی و کلاس است. ورزشکار باید بتواند بر اساس موقعیت، رشته، نوع باشگاه، نوع مربی، نوع کلاس، امکانات و تجهیزات، گزینه مناسب را پیدا و اطلاعات آن را مشاهده کند.

در این نسخه، Gym4Me علاوه بر کشف، رزرو سانس باشگاه و رزرو مستقل مربی را پوشش می‌دهد. برای تکمیل جریان محصول، پرداخت به‌صورت درگاه ماک با دو نتیجه «موفق» و «ناموفق» پیاده شده است؛ درگاه واقعی و تسویه مالی همچنان خارج از محدوده است.

## 2. هدف‌های MVP

- پیدا‌کردن باشگاه مناسب در کمترین زمان.
- پیدا‌کردن مربی بر اساس رشته، تخصص و محل فعالیت.
- پیدا‌کردن کلاس مناسب و مشاهده برنامه، مربی و باشگاه برگزارکننده.
- رزرو سانس باشگاه، زمین، کلاس یا مربی با کنترل اتمیک ظرفیت.
- درگاه پرداخت ماک برای رزروهای پولی؛ تأیید، رزرو را قطعی می‌کند و رد، ظرفیت را آزاد می‌کند.
- مشاهده و لغو رزرو با محاسبه بازپرداخت بر اساس قانون snapshot‌شده.
- نمایش اطلاعات استاندارد و قابل مقایسه برای همه باشگاه‌ها و مربی‌ها.
- جلوگیری از ایجاد دسته‌بندی‌ها، امکانات و تجهیزات تکراری.
- فراهم‌کردن یک پنل ساده برای ثبت اطلاعات توسط باشگاه‌دار و مربی.
- کنترل و انتشار اطلاعات توسط ادمین Gym4Me.

# 4. داده‌های مرجع تحت مدیریت ادمین

این داده‌ها فقط توسط ادمین Gym4Me ساخته می‌شوند. باشگاه‌دار یا مربی اجازه ساخت گزینه جدید ندارند و فقط از گزینه‌های موجود انتخاب می‌کنند.

## 4.1 اطلاعاتی که ادمین برای هر مورد وارد می‌کند

فرم ایجاد و ویرایش هر داده مرجع فقط شامل این موارد است:

- **نام**
- **عکس یا آیکن**
- **توضیحات**

شناسه، زمان ایجاد و زمان ویرایش به‌صورت خودکار توسط سیستم ساخته می‌شوند و فیلد ورودی ادمین نیستند.

برای داده‌های جغرافیایی، انتخاب والد نیز لازم است؛ برای مثال شهر باید به یک استان متصل شود.

## 4.2 انواع داده‌های مرجع

### نوع باشگاه

`club_types`

نمونه‌ها:

- باشگاه بدنسازی
- استخر
- مجموعه ورزشی
- آکادمی فوتبال
- باشگاه رزمی
- استودیو یوگا
- زمین ورزشی

باشگاه‌دار هنگام ساخت باشگاه یک یا چند نوع باشگاه را انتخاب می‌کند.

### نوع مربی

`coach_types`

نمونه‌ها:

- مربی خصوصی
- مربی گروهی
- مربی بدنسازی
- مربی آمادگی جسمانی
- سرمربی

مربی هنگام ساخت پروفایل یک یا چند نوع مربی را انتخاب می‌کند.

### نوع کلاس

`class_types`

نمونه‌ها:

- خصوصی
- نیمه‌خصوصی
- گروهی
- آنلاین
- حضوری

مربی یا باشگاه‌دار نوع کلاس‌های قابل ارائه را از این فهرست انتخاب می‌کند.

### رشته ورزشی

`sports`

نمونه‌ها:

- بدنسازی
- شنا
- یوگا
- فوتبال
- فوتسال
- بوکس
- تکواندو
- پیلاتس

باشگاه و مربی می‌توانند چند رشته را انتخاب کنند.

### امکانات

`amenities`

همه امکانات عمومی، رفاهی، دسترس‌پذیری و ایمنی در همین فهرست قرار می‌گیرند و دسته جداگانه‌ای برای آن‌ها ساخته نمی‌شود.

نمونه‌ها:

- پارکینگ
- رختکن
- دوش
- کمد
- بوفه
- سرویس بهداشتی
- آسانسور
- رمپ ویلچر
- کمک‌های اولیه
- سیستم تهویه
- نجات‌غریق
- وای‌فای

ادمین فقط نام، عکس و توضیحات امکان را تعریف می‌کند. باشگاه‌دار هنگام ساخت باشگاه:

1. امکان موجود را انتخاب می‌کند.
2. تعداد آن را وارد می‌کند.

برای امکاناتی که شمارش آن‌ها کاربرد ندارد، تعداد می‌تواند خالی بماند.

### تجهیزات

`equipment`

نمونه‌ها:

- تردمیل
- دوچرخه ثابت
- دمبل
- دستگاه پرس سینه
- تشک ورزشی
- توپ فوتبال
- میز پینگ‌پنگ

ادمین فقط نام، عکس و توضیحات تجهیز را تعریف می‌کند. باشگاه‌دار هنگام ساخت باشگاه:

1. تجهیز موجود را انتخاب می‌کند.
2. تعداد آن را وارد می‌کند.

### کشور

`countries`

- نام کشور
- عکس یا پرچم
- توضیحات

### استان

`provinces`

- انتخاب کشور
- نام استان
- عکس
- توضیحات

### شهر

`cities`

- انتخاب استان
- نام شهر
- عکس
- توضیحات

### منطقه شهری

`districts`

- انتخاب شهر
- نام منطقه
- عکس
- توضیحات

نمونه: منطقه ۱، منطقه ۲ یا نام رسمی منطقه.

### محدوده شهر

`city_regions`

- انتخاب شهر
- نام محدوده
- عکس
- توضیحات

مقادیر اصلی:

- شمال
- جنوب
- شرق
- غرب

هر باشگاه و مربی می‌تواند به یک یا چند محدوده مرتبط شود تا ورزشکار راحت‌تر جست‌وجو کند.

## 4.3 رفتار داده‌های مرجع

### P0

- ادمین می‌تواند یک مورد جدید ایجاد کند.
- ادمین می‌تواند نام، عکس و توضیحات را ویرایش کند.
- ادمین می‌تواند یک مورد را فعال یا غیرفعال کند.
- مقادیر غیرفعال برای انتخاب جدید نمایش داده نمی‌شوند.
- مقادیر انتخاب‌شده قبلی با غیرفعال‌شدن از پروفایل موجود حذف نمی‌شوند.
- باشگاه‌دار و مربی فقط می‌توانند گزینه‌های فعال را انتخاب کنند.
- حذف موردی که قبلاً توسط باشگاه یا مربی استفاده شده مجاز نیست.
- سیستم باید از ساخت نام تکراری در یک فهرست جلوگیری کند.

### P1

- هر نوع داده مرجع صفحه و فهرست مستقل دارد؛ برای مثال صفحه انواع باشگاه از صفحه امکانات جدا است.
- جست‌وجو با نام در هر فهرست مستقل.
- جست‌وجوی فارسی با یکسان‌سازی «ی/ي» و «ک/ك».
- فیلتر موارد فعال و غیرفعال.
- صفحه‌بندی نتایج.
- مرتب‌کردن موارد برای نحوه نمایش در فرم‌ها.
- مشاهده تعداد باشگاه‌ها یا مربی‌هایی که از یک مورد استفاده کرده‌اند.

## 4.4 مرزبندی مسئولیت ادمین و باشگاه‌دار

| داده       | ادمین تعریف می‌کند               | باشگاه‌دار وارد می‌کند          |
| ---------- | -------------------------------- | ------------------------------- |
| امکان      | نام، عکس، توضیحات                | انتخاب و تعداد                  |
| تجهیز      | نام، عکس، توضیحات                | انتخاب و تعداد                  |
| نوع باشگاه | نام، عکس، توضیحات                | انتخاب نوع                      |
| رشته       | نام، عکس، توضیحات                | انتخاب رشته‌های باشگاه          |
| نوع کلاس   | نام، عکس، توضیحات                | انتخاب نوع کلاس قابل ارائه      |
| موقعیت     | کشور، استان، شهر، منطقه و محدوده | انتخاب موقعیت، آدرس و نقطه نقشه |

# 9. سناریوهای اصلی

## S01 — پیدا‌کردن باشگاه در غرب شهر

1. ورزشکار شهر را انتخاب می‌کند.
2. محدوده «غرب» را انتخاب می‌کند.
3. نوع باشگاه و رشته را فیلتر می‌کند.
4. باشگاه‌های منطبق را مشاهده می‌کند.
5. وارد صفحه باشگاه می‌شود و مسیر یا شماره تماس را می‌بیند.

## S02 — پیدا‌کردن باشگاه دارای تجهیزات مشخص

1. ورزشکار نام رشته را جست‌وجو می‌کند.
2. تجهیز موردنظر، مانند تردمیل، را انتخاب می‌کند.
3. سیستم فقط باشگاه‌هایی را نمایش می‌دهد که آن تجهیز را ثبت کرده‌اند.
4. تعداد تجهیز در صفحه جزئیات باشگاه نمایش داده می‌شود.

## S03 — پیدا‌کردن باشگاه دارای امکانات مشخص

1. ورزشکار شهر را انتخاب می‌کند.
2. امکاناتی مانند پارکینگ، آسانسور و دوش را انتخاب می‌کند.
3. نتایج منطبق نمایش داده می‌شوند.
4. کاربر جزئیات و تعداد امکانات ثبت‌شده را در پروفایل باشگاه می‌بیند.

## S04 — پیدا‌کردن مربی

1. ورزشکار رشته ورزشی را انتخاب می‌کند.
2. نوع مربی و نوع کلاس را مشخص می‌کند.
3. شهر یا محدوده فعالیت را انتخاب می‌کند.
4. فهرست مربی‌های منطبق نمایش داده می‌شود.
5. کاربر وارد پروفایل مربی می‌شود و باشگاه‌های محل فعالیت را می‌بیند.

## S05 — جست‌وجو بدون نتیجه

1. ورزشکار چند فیلتر انتخاب می‌کند.
2. هیچ باشگاه یا مربی منطبق پیدا نمی‌شود.
3. سیستم پیام واضح نمایش می‌دهد.
4. کاربر می‌تواند یکی از فیلترها را حذف یا جست‌وجو را پاک کند.

## S06 — ایجاد نوع امکان توسط ادمین

1. ادمین وارد بخش امکانات می‌شود.
2. نام، عکس و توضیحات «پارکینگ» را وارد می‌کند.
3. سیستم تکراری‌نبودن نام را بررسی می‌کند.
4. امکان ذخیره و فعال می‌شود.
5. از این پس باشگاه‌دار می‌تواند آن را هنگام ساخت باشگاه انتخاب کند.

## S07 — انتخاب امکانات و تعداد توسط باشگاه‌دار

1. باشگاه‌دار وارد فرم ساخت یا ویرایش باشگاه می‌شود.
2. از فهرست تعریف‌شده توسط ادمین «پارکینگ» و «دوش» را انتخاب می‌کند.
3. تعداد هرکدام را وارد می‌کند.
4. اطلاعات را ذخیره می‌کند.
5. بعد از تأیید ادمین، امکانات و تعداد آن‌ها در صفحه باشگاه دیده می‌شوند.

## S08 — انتخاب تجهیزات و تعداد توسط باشگاه‌دار

1. باشگاه‌دار تجهیزات موجود را از فهرست ادمین انتخاب می‌کند.
2. تعداد هر تجهیز را وارد می‌کند.
3. نمی‌تواند تجهیز جدیدی خارج از فهرست ایجاد کند.
4. تجهیزات پس از تأیید پروفایل در صفحه عمومی نمایش داده می‌شوند.

## S09 — ساخت ساختار جغرافیایی

1. ادمین کشور را ایجاد می‌کند.
2. استان را به کشور متصل می‌کند.
3. شهر را به استان متصل می‌کند.
4. منطقه را به شهر متصل می‌کند.
5. محدوده شمال، جنوب، شرق یا غرب را برای شهر تعریف می‌کند.
6. باشگاه و مربی فقط از همین ساختار انتخاب می‌کنند.

## S10 — ثبت باشگاه و بررسی ادمین

1. باشگاه‌دار اطلاعات پایه، موقعیت، امکانات و تجهیزات را وارد می‌کند.
2. پروفایل را برای بررسی ارسال می‌کند.
3. ادمین اطلاعات را مشاهده می‌کند.
4. اگر اطلاعات کامل باشد آن را تأیید می‌کند.
5. در صورت نقص، دلیل رد را ثبت می‌کند تا باشگاه‌دار اصلاح کند.

## S11 — ثبت مربی و بررسی ادمین

1. مربی اطلاعات، رشته‌ها، نوع مربی و محل فعالیت را وارد می‌کند.
2. پروفایل را ارسال می‌کند.
3. ادمین پروفایل را تأیید یا همراه دلیل رد می‌کند.
4. فقط پروفایل تأییدشده در نتایج عمومی دیده می‌شود.

## S12 — اتصال مربی و باشگاه

1. باشگاه‌دار مربی ثبت‌شده را پیدا می‌کند.
2. درخواست همکاری ارسال می‌کند.
3. مربی درخواست را تأیید می‌کند.
4. مربی در صفحه باشگاه و باشگاه در صفحه مربی نمایش داده می‌شود.

## S13 — ویرایش داده مرجع استفاده‌شده

1. ادمین نام یا عکس یک امکان را ویرایش می‌کند.
2. تغییر در همه پروفایل‌هایی که آن امکان را انتخاب کرده‌اند نمایش داده می‌شود.
3. تعداد ثبت‌شده توسط هر باشگاه تغییر نمی‌کند.

## S14 — غیرفعال‌کردن داده مرجع

1. ادمین یک تجهیز را غیرفعال می‌کند.
2. تجهیز دیگر برای انتخاب جدید نمایش داده نمی‌شود.
3. در پروفایل باشگاه‌هایی که قبلاً آن را انتخاب کرده‌اند حذف نمی‌شود.

## S15 — ایجاد کلاس توسط باشگاه‌دار

1. باشگاه‌دار باشگاه برگزارکننده را انتخاب می‌کند.
2. نام، عکس، توضیحات، رشته و نوع کلاس را وارد می‌کند.
3. برنامه، ظرفیت و مخاطب کلاس را مشخص می‌کند.
4. مربی اصلی را از مربی‌های متصل به باشگاه انتخاب می‌کند.
5. کلاس را فعال می‌کند و کلاس در صفحه باشگاه و نتایج اپ دیده می‌شود.

## S16 — مشاهده لیست کلاس‌ها

1. باشگاه‌دار وارد بخش کلاس‌ها می‌شود.
2. کلاس‌ها را همراه وضعیت، مربی، تعداد شاگرد و ظرفیت مشاهده می‌کند.
3. بر اساس باشگاه یا مربی فیلتر می‌کند.
4. وارد جزئیات یک کلاس می‌شود و آن را ویرایش می‌کند.

## S17 — افزودن شاگرد به کلاس

1. باشگاه‌دار کلاس را باز می‌کند.
2. شماره موبایل شاگرد را جست‌وجو می‌کند.
3. کاربر ثبت‌شده را انتخاب یا اطلاعات ساده شاگرد جدید را وارد می‌کند.
4. سیستم تکراری‌نبودن و ظرفیت کلاس را بررسی می‌کند.
5. شاگرد به فهرست کلاس اضافه و ظرفیت باقی‌مانده به‌روزرسانی می‌شود.

## S18 — تغییر مربی کلاس

1. باشگاه‌دار کلاس دارای شاگرد را باز می‌کند.
2. مربی جدید را از مربی‌های متصل به باشگاه انتخاب می‌کند.
3. سیستم قبل از تغییر، هشدار نمایش می‌دهد.
4. مربی جدید جایگزین مربی قبلی می‌شود.
5. صفحه کلاس و پروفایل مربی‌ها به‌روزرسانی می‌شوند.

## S19 — کشف کلاس توسط ورزشکار

1. ورزشکار رشته، شهر، روز و بازه زمانی موردنظر را انتخاب می‌کند.
2. کلاس‌های فعال منطبق را مشاهده می‌کند.
3. صفحه کلاس را باز می‌کند و مربی، باشگاه، برنامه و ظرفیت را می‌بیند.
4. برای ثبت‌نام با باشگاه تماس می‌گیرد یا مسیر باشگاه را باز می‌کند.

# 14. معماری پیشنهادی NestJS + MongoDB

## 14.1 تصمیم اصلی

برای نسخه فعلی، معماری پیشنهادی **Modular Monolith** است؛ یعنی یک برنامه NestJS و یک دیتابیس MongoDB داریم، اما کد بر اساس دامنه‌های مستقل به ماژول‌های واضح تقسیم می‌شود.

در این مرحله Microservice پیشنهاد نمی‌شود. دامنه محصول هنوز در حال تغییر است، حجم ترافیک مشخص نیست و جداسازی زودهنگام سرویس‌ها هزینه توسعه، دیباگ، استقرار و هماهنگی داده‌ها را بالا می‌برد.

### نتیجه تصمیم

- یک Backend قابل استقرار با NestJS.
- یک Worker اختیاری برای کارهای پس‌زمینه.
- MongoDB به‌عنوان دیتابیس اصلی.
- Redis برای OTP، Rate Limit، Cache و Queue.
- Object Storage برای عکس‌ها.
- مرزهای ماژولی به‌گونه‌ای تعریف می‌شوند که در آینده بتوان ماژول پرترافیک را جدا کرد.

## 14.2 وضعیت فعلی پروژه

Backend فعلی پروژه NestJS نیست و با Hono، درایور مستقیم MongoDB و Redis نوشته شده است. چون کد Backend هنوز کوچک است، اگر تصمیم NestJS قطعی است، بهتر است مهاجرت همین حالا انجام شود؛ بعد از رشد ماژول‌های کلاس، شاگرد، مربی و ادمین هزینه بازنویسی بیشتر خواهد شد.

## 14.3 دیاگرام سطح بالا

```text
┌──────────────────────────────────────────────────────┐
│ Clients                                              │
│ Athlete App │ Business Panel │ Admin Panel │ Website │
└───────────────┬──────────────────────────────────────┘
                │ HTTPS / REST
                ▼
┌──────────────────────────────────────────────────────┐
│ NestJS API — Modular Monolith                        │
│ Auth │ Master Data │ Geo │ Club │ Coach │ Class      │
│ Enrollment │ Discovery │ Favorites │ Admin │ Media   │
└───────┬─────────────┬──────────────┬─────────────────┘
        │             │              │
        ▼             ▼              ▼
   MongoDB          Redis       Object Storage
   Main data     OTP/Cache/Jobs      Images
        ▲             │
        │             ▼
        └──── Optional Nest Worker ────► SMS Provider
```

## 14.4 سرویس‌های قابل استقرار موردنیاز

منظور از این بخش سرویس‌های واقعی زیرساختی است، نه هر ماژول داخل NestJS.

| سرویس          | برای شروع               | داده دائمی     | اثر قطعی موقت                                                       |
| -------------- | ----------------------- | -------------- | ------------------------------------------------------------------- |
| NestJS API     | ضروری                   | خیر            | همه درخواست‌های پویا متوقف می‌شوند                                  |
| MongoDB        | ضروری                   | بله            | خواندن و نوشتن داده اصلی متوقف می‌شود                               |
| Redis          | ضروری برای OTP          | خیر            | ورود جدید و Cache مختل می‌شود؛ داده اصلی از بین نمی‌رود             |
| Object Storage | ضروری                   | بله، برای فایل | آپلود عکس متوقف می‌شود؛ تصاویر قبلی ممکن است از CDN نمایش داده شوند |
| SMS Provider   | ضروری برای ورود موبایلی | خیر            | ارسال OTP و ورود جدید متوقف می‌شود                                  |
| Map Provider   | ضروری برای موقعیت       | خیر            | انتخاب/نمایش نقشه مختل می‌شود؛ آدرس متنی باقی می‌ماند               |
| Nest Worker    | قابل تعویق              | خیر            | Jobهای پس‌زمینه با تأخیر اجرا می‌شوند                               |

### 1. NestJS API — ضروری

وظایف:

- API اپ ورزشکار.
- API پنل باشگاه‌دار و مربی.
- API پنل ادمین.
- احراز هویت و مجوزها.
- اعتبارسنجی ورودی.
- اجرای قواعد دامنه.
- خواندن و نوشتن داده‌های MongoDB.

در MVP همه APIها در یک برنامه NestJS قرار می‌گیرند.

### 2. MongoDB — ضروری

محل نگهداری:

- کاربران و نشست‌ها.
- داده‌های مرجع.
- اطلاعات جغرافیایی.
- باشگاه‌ها و مربی‌ها.
- ارتباط باشگاه و مربی.
- کلاس‌ها.
- شاگردان کلاس.
- علاقه‌مندی‌ها و گزارش‌های کاربران.

برای محیط Production بهتر است MongoDB به‌صورت Replica Set یا سرویس مدیریت‌شده اجرا شود تا Backup، Failover و Transaction در دسترس باشد.

### 3. Redis — ضروری برای احراز هویت، مفید برای بقیه سیستم

کاربردها:

- نگهداری OTP با زمان انقضا.
- محدودیت تعداد درخواست OTP و ورود.
- Cache داده‌های مرجع و صفحه کشف.
- Queue اعلان‌ها در صورت اضافه‌شدن Worker.
- قفل کوتاه‌مدت عملیات حساس در صورت نیاز.

Redis منبع اصلی داده نیست و پاک‌شدن Cache نباید باعث ازدست‌رفتن اطلاعات باشگاه یا کلاس شود.

### 4. Object Storage — ضروری

برای نگهداری:

- تصاویر باشگاه.
- تصاویر مربی.
- تصاویر کلاس.
- تصاویر داده‌های مرجع.

فایل نباید به‌صورت Base64 یا Binary داخل MongoDB ذخیره شود. MongoDB فقط `key`، آدرس، نوع فایل، اندازه و مالک فایل را نگه می‌دارد.

می‌توان از سرویس S3-compatible استفاده کرد و CDN را بعداً جلوی آن قرار داد.

### 5. سرویس پیامک — ضروری برای OTP

- ارسال کد ورود.
- اعلان‌های ضروری در آینده.
- قرارگرفتن پشت یک Interface تا ارائه‌دهنده پیامک قابل تعویض باشد.

کد فعلی پروژه از Kavenegar پشتیبانی می‌کند و همین Adapter می‌تواند در NestJS منتقل شود.

### 6. سرویس نقشه — ضروری برای تجربه موقعیت

- انتخاب موقعیت باشگاه روی نقشه.
- نمایش موقعیت.
- بازکردن مسیریابی.
- تبدیل مختصات و آدرس در صورت نیاز.

منطق دامنه نباید مستقیم به SDK یک ارائه‌دهنده وابسته شود؛ یک `MapProvider` ساده امکان تعویض سرویس نقشه را فراهم می‌کند.

### 7. NestJS Worker — در شروع اختیاری

تا زمانی که فقط OTP داریم، می‌توان ارسال را از API انجام داد. با اضافه‌شدن اعلان تغییر مربی، پردازش تصویر یا بازسازی داده جست‌وجو، یک Worker جدا با BullMQ مناسب است.

وظایف آینده Worker:

- ارسال پیامک و Push.
- پردازش و Resize تصویر.
- به‌روزرسانی مدل جست‌وجو.
- Jobهای زمان‌بندی‌شده.

### سرویس‌هایی که فعلاً لازم نیستند

- Kafka یا RabbitMQ.
- Kubernetes.
- Elasticsearch/OpenSearch مستقل.
- API Gateway جداگانه.
- دیتابیس جدا برای هر ماژول.
- Microservice جدا برای باشگاه، مربی یا کلاس.

## 14.5 ماژول‌های داخل NestJS

### `AuthModule`

- درخواست و تأیید OTP.
- Access Token کوتاه‌عمر.
- Refresh Session.
- خروج از یک دستگاه یا همه دستگاه‌ها.
- Rate Limit.

وابستگی‌ها: `UsersModule`، Redis و سرویس پیامک.

### `UsersModule`

- پروفایل پایه کاربر.
- نقش‌های ورزشکار، باشگاه‌دار، مربی و ادمین.
- وضعیت حساب.
- کنترل دسترسی مبتنی بر نقش.

### `MasterDataModule`

این ماژول یک Collection عمومی ندارد؛ فقط قابلیت‌های مشترک داده‌های مرجع را کنار هم سازمان‌دهی می‌کند. هر نوع داده Service، Repository، Schema، Controller و Collection مستقل دارد:

| قابلیت     | Service             | Collection    |
| ---------- | ------------------- | ------------- |
| نوع باشگاه | `ClubTypesService`  | `club_types`  |
| نوع مربی   | `CoachTypesService` | `coach_types` |
| نوع کلاس   | `ClassTypesService` | `class_types` |
| رشته ورزشی | `SportsService`     | `sports`      |
| امکانات    | `AmenitiesService`  | `amenities`   |
| تجهیزات    | `EquipmentService`  | `equipment`   |

وظایف هر Service:

- ایجاد مورد با نام، عکس و توضیحات توسط ادمین.
- ویرایش اطلاعات.
- فعال یا غیرفعال‌کردن.
- دریافت یک مورد با ID.
- نمایش فهرست صفحه‌بندی‌شده.
- جست‌وجو با نام نرمال‌شده.
- فیلتر فعال/غیرفعال برای ادمین.
- برگرداندن فقط موارد فعال به اپ و پنل باشگاه‌دار.
- جلوگیری از ایجاد نام تکراری.
- جلوگیری از حذف مورد استفاده‌شده.

برای کم‌کردن کد تکراری می‌توان یک `BaseMasterDataService` و `BaseMasterDataRepository` داخلی داشت؛ اما هر Service باید Model و Collection مخصوص خود را دریافت کند. بنابراین اشتراک کد داریم، نه اشتراک داده.

### `GeographyModule`

- `CountriesService` با Collection مستقل `countries`.
- `ProvincesService` با Collection مستقل `provinces`.
- `CitiesService` با Collection مستقل `cities`.
- `DistrictsService` با Collection مستقل `districts`.
- `CityRegionsService` با Collection مستقل `city_regions` برای شمال، جنوب، شرق و غرب.
- کنترل رابطه والد و فرزند.
- ارائه گزینه‌های وابسته برای فرم‌ها و فیلترها.
- جست‌وجو و صفحه‌بندی داخل هر سطح جغرافیایی.
- محدودکردن جست‌وجوی استان به کشور و شهر به استان انتخاب‌شده.

### `MediaModule`

- ساخت مجوز آپلود.
- ثبت Metadata فایل.
- اتصال تصویر به مالک مجاز.
- حذف امن فایل بلااستفاده.
- محدودیت فرمت و اندازه.

### `ClubsModule`

- ایجاد و ویرایش باشگاه.
- موقعیت و اطلاعات تماس.
- انتخاب نوع، رشته، امکانات و تجهیزات.
- ثبت تعداد امکانات و تجهیزات.
- وضعیت بررسی ادمین.
- صفحه عمومی باشگاه.

### `CoachesModule`

- پروفایل مربی.
- نوع مربی، رشته و نوع کلاس.
- محدوده فعالیت.
- وضعیت بررسی ادمین.
- صفحه عمومی مربی.

### `ClubCoachesModule`

- درخواست اتصال باشگاه و مربی.
- تأیید یا رد ارتباط.
- فهرست مربی‌های باشگاه.
- جلوگیری از تخصیص مربی نامرتبط به کلاس.

این ارتباط بهتر است Collection مستقل باشد و به‌صورت آرایه ساده داخل باشگاه ذخیره نشود؛ چون وضعیت و تاریخ ارتباط اهمیت دارد.

### `ClassesModule`

- ایجاد، ویرایش و غیرفعال‌کردن کلاس.
- برنامه هفتگی ساده.
- ظرفیت.
- مربی اصلی و مربیان کمکی.
- نمایش عمومی کلاس.
- فیلتر بر اساس رشته، نوع، زمان، موقعیت، باشگاه و مربی.

### `EnrollmentsModule`

در این MVP منظور از Enrollment عضویت مدیریتی شاگرد در کلاس است، نه خرید یا رزرو آنلاین.

- فهرست شاگردان کلاس.
- افزودن کاربر ثبت‌شده.
- افزودن شاگرد ساده با نام و شماره موبایل.
- حذف یا انتقال شاگرد.
- بررسی ظرفیت.
- جلوگیری از ثبت تکراری.

### `DiscoveryModule`

- صفحه خانه.
- جست‌وجوی یکپارچه.
- فیلتر باشگاه، مربی و کلاس.
- نتایج لیستی و نقشه‌ای.
- باشگاه‌ها، مربی‌ها و کلاس‌های پیشنهادی.

این ماژول مالک داده باشگاه یا مربی نیست؛ فقط از ماژول‌های مالک داده Query می‌گیرد و خروجی مناسب اپ تولید می‌کند.

### `FavoritesModule` — P1

- ذخیره باشگاه، مربی یا کلاس.
- فهرست علاقه‌مندی‌ها.
- حذف علاقه‌مندی.

### `ReviewsModule` — P1

- ثبت امتیاز و نظر.
- گزارش نظر.
- پاسخ باشگاه.
- Moderation ادمین.

### `AdminModule`

- داشبورد ساده.
- صف بررسی باشگاه و مربی.
- غیرفعال‌کردن کلاس نامناسب.
- مدیریت محتوای کشف.
- مدیریت گزارش‌های اطلاعات اشتباه.

`AdminModule` نباید منطق باشگاه یا داده‌های مرجع را دوباره پیاده کند؛ فقط Use Caseهای ادمین را از ماژول مربوط فراخوانی می‌کند.

### `NotificationsModule` — P1

- تعریف پیام.
- Queue ارسال.
- پیامک و Push.
- اعلان تغییر مربی کلاس.

### `AuditModule` — سبک ولی ضروری

- ثبت ایجاد و ویرایش داده مرجع.
- ثبت تأیید یا رد باشگاه و مربی.
- ثبت تغییر مربی و حذف شاگرد.
- نگهداری actor، action، target و زمان.

### جریان ۱: جست‌وجوی نوع باشگاه در پنل ادمین

```text
Admin UI
  → GET /api/v1/admin/catalog/club-types?q=بدن
  → ClubTypesController
  → ClubTypesService.search()
  → normalizePersian("بدن")
  → ClubTypesRepository.search()
  → MongoDB club_types با Index normalizedName
  → پاسخ صفحه‌بندی‌شده
```

`ClubTypesController` به `coach_types` یا Collection دیگری دسترسی ندارد. جست‌وجوی هر نوع از Controller و Repository همان نوع عبور می‌کند.

### جریان ۲: ساخت باشگاه و انتخاب امکانات

```text

  → دریافت amenities فعال از AmenitiesService

  → POST /business/clubs

  → اعتبارسنجی فعال‌بودن IDها از AmenitiesService
  → ذخیره [{ amenityId, quantity }] در clubs
```

نام یا عکس امکان داخل `clubs` کپی نمی‌شود. در زمان نمایش، اطلاعات `amenities` با IDها خوانده می‌شود؛ بنابراین تغییر نام «پارکینگ» توسط ادمین بلافاصله در همه باشگاه‌ها دیده می‌شود و تعداد ثبت‌شده باشگاه تغییر نمی‌کند.

### جریان ۳: جست‌وجوی باشگاه توسط ورزشکار

```text

  → GET /public/clubs?cityId=...&clubTypeId=...&amenityIds=...
  → DiscoveryController
  → DiscoveryService
```

داده‌های مرجع برای هر باشگاه جداگانه Query نمی‌شوند؛ همه IDهای صفحه جمع‌آوری و در چند Query گروهی Resolve می‌شوند تا مشکل N+1 ایجاد نشود.

### جریان ۴: افزودن شاگرد به کلاس

```text

  → POST /business/classes/:id/students
  → EnrollmentsService
  → بررسی مالکیت باشگاه
  → بررسی تکراری‌نبودن موبایل
  → بررسی ظرفیت کلاس
  → Transaction: ایجاد enrollment + افزایش studentCount
  → AuditModule
```

اگر هر مرحله Transaction شکست بخورد، نه شاگرد ثبت می‌شود و نه شمارنده کلاس تغییر می‌کند.

### جریان ۵: تغییر مربی کلاس

```text
Business Panel
  → PUT /business/classes/:id/coaches
  → ClassesService
  → بررسی مالکیت کلاس
  → ClubCoachesService: آیا مربی با باشگاه ارتباط فعال دارد؟
  → بررسی وجود دقیقاً یک مربی اصلی
  → ذخیره coachAssignments
  → AuditModule
  → NotificationsModule در فاز P1
```

اگر مربی به باشگاه متصل نباشد، درخواست با خطای `COACH_NOT_CONNECTED_TO_CLUB` رد می‌شود.

## 14.8 انتخاب روش اتصال NestJS به MongoDB

پیشنهاد این پروژه استفاده از `@nestjs/mongoose` است.

دلایل:

- اتصال طبیعی به Dependency Injection و Moduleهای NestJS.
- تعریف Schema و Index در کنار هر دامنه.
- Validation و Hookهای قابل کنترل.
- پشتیبانی مناسب از Session و Transaction.
- سرعت توسعه بیشتر برای تیم کوچک.

برای جلوگیری از وابستگی منطق محصول به Mongoose، Modelها فقط در Repository استفاده می‌شوند و Controller مستقیماً با Model کار نمی‌کند.

### گزینه جایگزین

استفاده از درایور مستقیم `mongodb` کنترل بیشتر و لایه سبک‌تری می‌دهد، اما Boilerplate اتصال، Tokenهای DI، Mapping و Repository بیشتر می‌شود. کد فعلی از این روش استفاده می‌کند؛ با مهاجرت به NestJS، مزیت سادگی `@nestjs/mongoose` برای این پروژه بیشتر است.

## 14.10 استراتژی Reference و Embed در MongoDB

### Embed شود

- ساعات کاری باشگاه.
- امکانات و تعداد آن‌ها.
- تجهیزات و تعداد آن‌ها.
- برنامه ساده کلاس.
- مربی‌های کلاس، چون تعدادشان کم و همراه کلاس خوانده می‌شوند.

### Reference شود

- داده‌های مرجع ادمین.
- کاربران و مالک باشگاه.
- ارتباط باشگاه و مربی.
- شاگردان کلاس.
- تصاویر.

قاعده: داده‌ای که مستقل رشد می‌کند، مجوز متفاوت دارد یا جداگانه Query می‌شود Reference است. داده کوچک و وابسته به عمر والد Embed می‌شود.

## 14.11 جست‌وجو و Discovery

### جست‌وجوی داده‌های مرجع

هر Collection جست‌وجوی مستقل دارد. نمونه درخواست:

```text

GET /api/v1/admin/catalog/amenities?q=پارک&page=1&limit=20

```

پارامترهای استاندارد:

| پارامتر    | کاربرد                                               |
| ---------- | ---------------------------------------------------- |
| `q`        | جست‌وجوی نام                                         |
| `isActive` | فیلتر فعال یا غیرفعال؛ فقط برای ادمین                |
| `page`     | شماره صفحه                                           |
| `limit`    | تعداد نتیجه، حداکثر ۱۰۰                              |
| `sort`     | مرتب‌سازی نام، جدیدترین یا قدیمی‌ترین                |
| شناسه والد | محدودکردن استان به کشور، شهر به استان و منطقه به شهر |

جریان جست‌وجو:

1. مقدار `q` Trim می‌شود.
2. حروف فارسی و عربی یکسان می‌شوند.
3. اعراب، نیم‌فاصله نامعتبر و فاصله تکراری حذف می‌شود.
4. مقدار نهایی با `normalizedName` مقایسه می‌شود.
5. API عمومی شرط `isActive=true` را به‌صورت اجباری اضافه می‌کند.
6. نتیجه با Pagination و تعداد کل بازگردانده می‌شود.

برای داده‌های مرجع که معمولاً تعداد کمی دارند، Prefix Search ایندکس‌شده کافی است:

```text
normalizedName startsWith normalized(q)
```

جست‌وجوی بدون ابتدای عبارت مانند Regex آزاد روی کل متن پیشنهاد نمی‌شود؛ چون با بزرگ‌شدن داده Index مؤثر نخواهد بود. اگر بعداً جست‌وجوی غلط املایی، بخشی از کلمه یا توضیحات لازم شد، برای هر Collection یک Index در Atlas Search تعریف می‌شود.

نمونه پاسخ:

```json
{
  "data": [
    {
      "id": "...",
      "name": "باشگاه بدنسازی",
      "image": { "url": "https://..." },
      "description": "...",
      "isActive": true
    }
  ],
  "meta": {
    "page": 1,
    "limit": 20,
    "total": 1
  }
}
```

### جست‌وجوی باشگاه، مربی و کلاس در MVP

- فیلترها بر اساس ID داده‌های مرجع انجام می‌شوند.
- نام فارسی در فیلد نرمال‌شده جدا ذخیره می‌شود.
- نرمال‌سازی شامل یکسان‌سازی «ی/ي»، «ک/ك»، حذف اعراب، فاصله‌های اضافه و تبدیل اعداد است.
- Query عمومی فقط `reviewStatus=approved` و `visibility=public` را برمی‌گرداند.
- Projection کارت نتایج کوچک نگه داشته می‌شود.
- Pagination ترجیحاً Cursor-based است؛ برای پنل ساده ادمین Page-based هم قابل قبول است.
- فیلتر نزدیک من با Index نوع `2dsphere` انجام می‌شود.

برای جست‌وجوی نام، Regex بدون ابتدا و روی Collection بزرگ مناسب نیست. اگر MongoDB Atlas استفاده شود، Atlas Search انتخاب اول برای Autocomplete و جست‌وجوی فارسی است. در شروع می‌توان Exact/Prefix Search روی فیلد نرمال‌شده داشت و Search پیشرفته را پس از وجود داده واقعی اضافه کرد.

### Cache

- فهرست‌های فعال `club_types`، `coach_types`، `class_types`، `sports`، `amenities` و `equipment` جداگانه با TTL کوتاه در Redis Cache می‌شوند.
- سکشن‌های صفحه خانه Cache می‌شوند.
- نتیجه جست‌وجوی شخصی یا بسیار متنوع در شروع Cache نمی‌شود.
- با تغییر هر Collection مرجع، فقط Cache همان Collection Invalid می‌شود.
- با انتشار باشگاه، مربی یا کلاس، Cache مربوط به Discovery پاک می‌شود.

## 14.13 احراز هویت و مجوزها

- OTP در Redis با TTL و محدودیت تلاش ذخیره می‌شود.
- Access Token کوتاه‌عمر است.
- Refresh Token برای هر دستگاه جدا و به‌صورت Hash در MongoDB ذخیره می‌شود.
- `JwtAuthGuard` هویت را بررسی می‌کند.
- `RolesGuard` نقش کلی را بررسی می‌کند.
- Policy سطح منبع بررسی می‌کند کاربر واقعاً مالک آن باشگاه یا مجاز به دیدن شاگردان کلاس است.
- صرف داشتن نقش `club_owner` اجازه ویرایش هر باشگاهی را نمی‌دهد.
- شماره موبایل شاگرد در API عمومی هرگز Serialize نمی‌شود.

## 14.14 سازگاری و Transaction

Transaction فقط برای عملیات چندسندی مهم استفاده شود:

- افزودن شاگرد و افزایش شمارنده کلاس.
- حذف یا انتقال شاگرد و اصلاح شمارنده‌ها.
- عملیات آینده رزرو و ظرفیت.

برای عملیات ساده مانند ویرایش توضیحات باشگاه، Atomic Update یک سند کافی است.

در همه Updateها بهتر است `updatedAt` و در عملیات حساس `version` بررسی شود تا ویرایش هم‌زمان باعث ازدست‌رفتن تغییرات نشود.

## 14.18 مسیر مقیاس‌پذیری

### مرحله اول

- یک NestJS API.
- یک MongoDB Replica Set.
- یک Redis.
- Object Storage.
- بدون Microservice.

### پس از رشد ترافیک

- چند Instance از API پشت Load Balancer.
- Worker جدا برای اعلان و تصویر.
- CDN برای تصاویر.

### فقط در صورت وجود نیاز واقعی

- جداکردن Discovery/Search به سرویس مستقل اگر بار خواندن بسیار زیاد شد.

- جداکردن Notifications اگر حجم ارسال بالا رفت.
- جداکردن Booking/Payments در زمان اضافه‌شدن تراکنش‌های مالی.

مرزهای ماژولی فعلی این جداسازی آینده را ممکن می‌کنند؛ اما از روز اول هزینه Microservice تحمیل نمی‌شود.

## 14.21 ADR: Collection مستقل برای داده‌های مرجع

**وضعیت:** پذیرفته‌شده  
**تاریخ:** ۱۲ شهریور ۱۴۰۵

### زمینه

انواع باشگاه، مربی، کلاس، رشته، امکانات و تجهیزات در حال حاضر ساختار نمایشی مشابهی دارند، اما در پنل ادمین صفحه، جست‌وجو، Endpoint و مسیر توسعه مستقل می‌خواهند.

### تصمیم

هر نوع داده در Collection مستقل ذخیره می‌شود. کدهای مشترک CRUD و جست‌وجو از طریق Base Service و Base Repository بازاستفاده می‌شوند.

### گزینه‌های بررسی‌شده

| گزینه                             | سادگی دیتابیس | استقلال Query و Index |       توسعه آینده | نتیجه     |
| --------------------------------- | ------------: | --------------------: | ----------------: | --------- |
| یک `catalog_items` با فیلد `type` |          بالا |                 متوسط |             متوسط | رد شد     |
| Collection مستقل برای هر نوع      |         متوسط |                  بالا |              بالا | انتخاب شد |
| دیتابیس مستقل برای هر نوع         |         پایین |                  بالا | بالا ولی غیرضروری | رد شد     |

### پیامدها

- جست‌وجوی `club_types` مستقیم روی Collection خودش انجام می‌شود.
- هر نوع Endpoint و Index مستقل دارد.
- Routeها برای نظم API زیر Namespace مشترک `/catalog` قرار می‌گیرند، ولی Storage مشترک ندارند.
- Routeهای جغرافیایی زیر `/catalog/locations` گروه‌بندی می‌شوند.
- هیچ شرط `type` در Queryهای داده مرجع وجود ندارد.
- افزودن فیلد اختصاصی به یک نوع، بقیه Collectionها را تحت تأثیر قرار نمی‌دهد.
- تعداد فایل‌های Schema و Repository بیشتر می‌شود.
- Base Service و Base Repository باید طوری نوشته شوند که استقلال Collectionها را از بین نبرند.

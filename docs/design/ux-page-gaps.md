# ممیزی صفحات و مسیرهای UX اپلیکیشن

بررسی از روی مسیرهای `apps/application/app`، اتصال دکمه‌ها و فرم‌ها به API و وضعیت فعلی کد انجام شده است. هدف، تبدیل کارهای چندمرحله‌ای به مسیر مستقل است؛ نه ساخت صفحه برای هر کنترل کوچک.

## کمبود صفحهٔ مستقل — پیاده‌سازی این مرحله

| نیاز | مشکل قبلی | مسیر جدید |
| --- | --- | --- |
| درخواست مربیگری | فرم با state داخل انتخاب نقش جایگزین می‌شد؛ لینک مستقیم و رفرش وضعیت فرم را حفظ نمی‌کرد | `/auth/roles/coach` |
| درخواست مالک باشگاه | فرم مستقل در درخت مسیرها وجود نداشت | `/auth/roles/owner` |
| پیگیری درخواست نقش | فقط وضعیت روی کارت نقش و اعلان گذرا بعد از ارسال | `/auth/roles/requests` |
| ثبت تیکت ورزشکار | فرم داخل فهرست درخواست‌ها باز می‌شد | `/athlete/support/new` |
| گفت‌وگوی تیکت ورزشکار | همهٔ پیام‌ها و فرم‌های پاسخ در فهرست نمایش داده می‌شد | `/athlete/support/[ticketId]` |
| پشتیبانی مربی | تنظیمات مربی به وب‌سایت خارجی می‌رفت | `/coach/support` |
| ثبت تیکت مربی | مسیر داخل حساب مربی وجود نداشت | `/coach/support/new` |
| گفت‌وگوی تیکت مربی | مسیر مستقل برای پیگیری وجود نداشت | `/coach/support/[ticketId]` |
| جزئیات عضویت و سوابق مصرف | جزئیات و سوابق داخل کارت فهرست باز می‌شد | `/athlete/memberships/[entitlementId]` |

### رفتار مورد انتظار

- صفحهٔ نقش‌ها فقط انتخاب و نمایش وضعیت دارد؛ فرم روی همان URL باز نمی‌شود.
- درخواست نقش از لینک مستقیم باز می‌شود. کاربر مهمان پس از ورود به همان فرم برمی‌گردد. لینک بازگشت مقصد مشخص دارد.
- ارسال موفق به صفحهٔ پیگیری می‌رود. درخواست در انتظار/تأییدشده دوباره ارسال نمی‌شود؛ درخواست ردشده امکان ارسال دوباره دارد. دلیل رد در قرارداد API موجود نیست و متن ساختگی نمایش داده نمی‌شود.
- ثبت تیکت به گفت‌وگوی همان تیکت می‌رود. ارتباط تیکت با سفارش، پیام‌ها، پاسخ و وضعیت بسته/باز حفظ شده‌اند. لینک‌های قبلی دارای اطلاعات سفارش به صفحهٔ ثبت جدید هدایت می‌شوند.
- تیکت ناموجود یا خارج از فهرست حساب، حالت «در دسترس نیست» دارد. مسیرها زیر احراز هویت موجود اپ قرار دارند؛ مجوز واقعی داده همچنان مسئولیت API است.
- سوابق مصرف عضویت از مسیر مستقل، با همان صفحه‌بندی و دادهٔ واقعی خوانده می‌شود.
- تم، رنگ سبز برند، Secondary Header و هیروهای گرادیانت/blur مشترک حفظ شده‌اند.

## کارهایی که هنوز برای کامل شدن محصول باقی‌اند

این موارد را نباید با «نداشتن طراحی صفحه» اشتباه گرفت؛ UI بخشی از آن‌ها موجود است اما جریان عملیاتی کامل نیست:

| جریان | وضعیت فعلی در کد | کار لازم |
| --- | --- | --- |
| ثبت نظر مربی و کلاس | مسیرهای `/reviews/new` موجودند ولی `DiscoveryReviewFormScreen` برای این دو نوع حالت غیرفعال نمایش می‌دهد | API ثبت نظر، احراز واجد شرایط بودن و اتصال فرم موجود |

این مرحله این قابلیت‌ها را فعال یا کامل اعلام نمی‌کند. تکمیل آن‌ها کار بک‌اند و منطق محصول می‌خواهد، نه افزودن فرم نمایشی دیگر.

## بخش‌هایی که صفحهٔ جدید لازم ندارند

- تأیید حذف، انتخاب فیلتر، انتخاب تاریخ/ساعت و ویرایش یک فیلد کوتاه: دیالوگ یا bottom sheet مناسب است.
- قوانین، حریم خصوصی و حذف اطلاعات: صفحات آن‌ها در `apps/website` موجود است؛ لینک خارجی فعلی به معنی صفحهٔ مفقود نیست.
- پرداخت و نتیجهٔ پرداخت: جریان و UI اختصاصی موجود دارند؛ ساخت نسخهٔ موازی فقط مسیرها را پیچیده می‌کند.
- مدیریت داخلی مالک باشگاه: پروژهٔ `apps/business` موجود است؛ ورود نقش مالک باید به همان محصول متصل بماند.

## جزئیات فنی اعتبارسنجی

مسیرهای درخواست نقش زیر AuthGate هستند و فقط سه مقصد شناخته‌شدهٔ درخواست/پیگیری در allowlist بازگشت بعد از ورود قرار گرفته‌اند؛ مسیر ورود و تنظیم رمز همچنان مقصد بازگشت مجاز نیستند. به‌روزرسانی وضعیت نقش، اطلاعات حساب را هم تازه می‌کند. تنظیم کاهش حرکت اکنون در انیمیشن‌های جابه‌جایی صفحه رعایت می‌شود تا کپی خروجی صفحه، کنترل‌های هم‌پوشان نسازد.

داده‌های دمو نمونه‌اند. ارسال واقعی درخواست نقش، تیکت یا تغییر دسترسی حساب تولیدی انجام نشده است.

نتیجهٔ بررسی: بیلد نهایی و TypeScript، ESLint فایل‌های مرتبط و کنترل ۷۱ توکن طراحی پاس شدند. ۹ تست متمایز مرورگر و ۴ تست مسیریابی پاس شدند؛ شامل ارسال/پیگیری نقش، تازه‌سازی دسترسی تأییدشده، ثبت/پاسخ تیکت، رفرش لینک‌ها، اتصال سفارش، صفحه‌بندی مصرف عضویت و برگشت پس از ورود. تصاویر ۸ صفحه در دو تم و عرض‌های ۳۷۵ و ۸۲۰ ثبت شده‌اند؛ گالری ۱۶ تصویر موبایل را در هر دو تم نمایش می‌دهد.

## اصلاح گزارش تغییر زمان رزرو

تغییر زمان رزرو پیاده‌سازی شده است: APIهای `POST /reservations/:id/reschedule/quote` و `POST /reservations/:id/reschedule` به فرم تأیید متصل‌اند. انتقال اتمی با کلید تکرارناپذیری انجام می‌شود؛ لغو رزرو قبلی پس از تأیید رزرو جدید است. پرداخت اختلاف قیمت همچنان شبیه‌سازی است. گزارش قبلی این بخش قدیمی بود.

## خرید خدمات مربی — پیاده‌سازی شد

- `/athlete/packages/[coachSlug]`: انتخاب بسته یا خدمت ماهانه و تأیید پرداخت آزمایشی.
- `/athlete/packages`: اعتبارهای خریداری‌شده، ادامه پرداخت و انتخاب سانس.
- قیمت و تعداد جلسات هنگام خرید روی سرور ثبت می‌شوند؛ ماهانه ۳۰ روز از پرداخت معتبر است، بدون تمدید خودکار. بسته جلسه‌ای تا مصرف جلسات معتبر است.
- رزرو فقط از اعتبار همان خدمت مصرف می‌کند؛ آخرین اعتبار در تراکنش اتمی مصرف می‌شود. لغو مربی یا لغو ورزشکار با بازپرداخت کامل، اعتبار جلسه را برمی‌گرداند. لغو دیرهنگام اعتبار را مصرف می‌کند.
- پرداخت و دفتر مالی از جریان مشترک Commerce استفاده می‌کنند؛ اتصال بانکی واقعی همچنان خارج از این پیاده‌سازی است.
- دستیار بیزینس از ناوبری حذف شد؛ آدرس قدیمی `/coach` در بیزینس به `/data` منتقل می‌شود.

اعتبارسنجی این تغییر: ۳۴ تست بک‌اند در چهار suite خرید/رزرو/پرداخت؛ تست مرورگر خرید موفق و ناموفق، ماندگاری اعتبار پس از رفرش و تغییر زمان رزرو؛ build اپلیکیشن و بررسی TypeScript اپلیکیشن، بیزینس و بک‌اند موفق بودند. تست‌های دیتابیس با MongoDB موقت و تست‌های مرورگر با API آزمایشی اجرا شدند.
